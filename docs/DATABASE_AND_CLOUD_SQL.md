# AMAL — Database Architecture, Migration Workflow & Cloud SQL Readiness

## 1. Database Architecture & Source of Truth

- **Source of Truth**: `src/db/schema.ts` (38 PostgreSQL tables) paired with `src/db/rls.sql` (Row-Level Security, least-privilege grants, and `SECURITY DEFINER` lookup functions).
- **Tracked Migrations**: `drizzle/` generated by Drizzle Kit (`src/db/drizzle.config.ts`) containing:
  - `drizzle/0000_initial_baseline.sql`
  - `drizzle/meta/_journal.json`
  - `drizzle/meta/0000_snapshot.json`
- **Core Design Guarantees**:
  - **Tenant Isolation**: 33 tenant-owned tables enforce `FORCE ROW LEVEL SECURITY` using `NULLIF(current_setting('app.current_tenant_id', true), '')::uuid`.
  - **Branch/Outlet Integrity**: Composite foreign keys (`tenant_id`, `branch_id`, `outlet_id`) prevent cross-tenant and cross-branch references across orders, QR stations, inventory, and staff scopes.
  - **Monetary Precision**: All ETB prices, variations, modifiers, VAT, and totals are stored as integer minor units (*santim*) in `BIGINT` columns.

## 2. PostgreSQL Role Responsibilities

| Role | Privileges | Purpose | Used By |
| :--- | :--- | :--- | :--- |
| **`amal_admin`** | Schema owner (superuser in local dev; Cloud SQL owner/migrator role in prod) | Runs DDL migrations (`drizzle/*.sql`), applies `src/db/rls.sql`, seeds canonical `roles` & presets (`src/db/seed.ts`) | `db:migrate`, `db:baseline`, `db:rls`, `db:seed` **only** |
| **`amal_app`** | `NOSUPERUSER`, `NOBYPASSRLS`, `LOGIN` | Runtime API queries inside transaction-scoped `withTenantTransaction()`. Cannot bypass RLS; read-only on `roles`; append-only on `audit_logs`, `inventory_movements`, `loyalty_ledger`, `platform_admin_impersonation_logs`; no `DELETE` on `payment_webhook_events` | Express runtime (`server.ts`, `pool` in `src/db/index.ts`) |

## 3. Row-Level Security & Pooling Design

- Every tenant-scoped backend operation runs inside `withTenantTransaction(tenantId, fn)` (`server/db/tenantTx.ts`), which:
  1. Validates `tenantId` as a strict UUID (`assertValidUuid`).
  2. Executes `SELECT set_config('app.current_tenant_id', $1, true)` inside `BEGIN ... COMMIT/ROLLBACK`.
  3. Because `is_local = true`, PostgreSQL clears `app.current_tenant_id` automatically when the transaction ends — guaranteeing zero tenant leakage across pooled connections.
- **Pre-Tenant Lookup Security**: Six narrow `SECURITY DEFINER` functions in `src/db/rls.sql` (`resolve_public_storefront_context`, `list_user_tenant_memberships`, `list_platform_tenant_summaries`, `resolve_staff_invitation_by_hash`, `resolve_payment_tx_by_ref`, `list_tenants_with_expired_reservations`) execute with `SET search_path = pg_catalog, public`, schema-qualified `public.*` table names, and `REVOKE ALL ... FROM PUBLIC` / `GRANT EXECUTE ... TO amal_app`.

| Variable | Local Development | Preview / Staging | Production (Google Cloud SQL) |
| :--- | :--- | :--- | :--- |

| `SQL_HOST` / `SQL_PORT` | `127.0.0.1` / `5432` | Staging Postgres / Proxy host | `127.0.0.1` (Cloud SQL Auth Proxy) or private VPC IP |

## 5. Standard Migration Workflow

Use the existing npm scripts (`package.json`):

1. **Generate migration** after modifying `src/db/schema.ts`:
   ```bash
   npm run db:generate -- --name=<descriptive_change>
   ```
2. **Review generated SQL** in `drizzle/<idx>_<name>.sql` for any destructive statements (`DROP`, `TRUNCATE`, column data loss) and verify consistency:
   ```bash
   npm run db:check
   ```
3. **Execute locally** (`amal_dev`):
   ```bash
   npm run db:migrate
   ```
   *(If initializing tracking on an already-synced pre-baseline database without resetting data, run `npm run db:baseline` once first.)*
4. **Verify migration & RLS status**:
   ```bash
   npm run db:status
   ```
5. **Promote to Preview / Staging**:
   Run with staging environment variables injected (using `SQL_ADMIN_USER` / `SQL_ADMIN_PASSWORD` in the migration step only):
   ```bash
   SQL_DB_NAME=amal_staging npm run db:migrate
   SQL_DB_NAME=amal_staging npm run db:status
   ```
6. **Promote to Production Cloud SQL** *(only after explicit approval + verified backup)*:
   - Take an on-demand Cloud SQL backup snapshot.
   - Connect via Cloud SQL Auth Proxy or private VPC migration job using `amal_admin`.
   - Run `npm run db:migrate` followed by `npm run db:status`.
   - Confirm `/api/v1/health` returns `200 {"ok":true,"db":"connected"}`.

## 6. Cloud SQL Deployment, Backup & Rollback Procedure

- **Compatibility Verified**: PostgreSQL 15 (`gen_random_uuid()` built-in, no external extension requirement), `pg` driver + `drizzle-orm` `0.45.x`, and `SQL_SSL` / `PG_POOL_MAX` environment controls.
- **Connection Pooling**: Keep `Cloud SQL Auth Proxy` sidecar on Cloud Run (`127.0.0.1:5432`) with `PG_POOL_MAX=10`, or enable `SQL_SSL=true` over Private Service Connect / VPC.
- **Backup Strategy**:
  - Enable automated daily Cloud SQL backups + **Point-in-Time Recovery (PITR)** transaction logs (7–30 day retention).
  - Always trigger a manual pre-migration Cloud SQL backup before applying any schema migration to production.
- **Rollback Strategy**:
  - Prefer **forward-fix** migrations over editing applied migration history.
  - For destructive incidents or failed cutovers, restore from the pre-migration Cloud SQL snapshot / PITR timestamp to a recovery instance, verify data + `npm run db:status`, and repoint runtime traffic.
